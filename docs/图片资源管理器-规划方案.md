# 图片资源管理器 · 规划方案

> 一句话定位：把"设计出的图"变成"客户端可以直接依赖的库"的一条自动化流水线。
> 设计只管上传，客户端只管升版本号。

---

## 一、问题与目标

### 现状痛点
- 设计给图 → 客户端手动导入项目，靠 IM/网盘传，容易漏、容易错、容易版本不一致。
- 没有统一的命名规范，三端各写各的，改图靠吼。
- 无法追溯"这次到底改了哪些图"。

### 目标工作流
1. 设计师在 Web 面板**批量上传**图片。
2. 平台自动完成：命名规范化、多倍图/矢量派生、去重校验、快照记录。
3. 平台自动构建三端资源库产物并**发布到私有仓库**。
4. 客户端**只改依赖版本号**即可拿到新资源。
5. 开发在面板上能看到"本次更新了哪些图"（新增/修改/删除）。

### 角色
| 角色 | 权限 |
|---|---|
| 设计师 | 上传（批量）、编辑元数据/标签、发起发布、查看自己上传 |
| 开发 | 查看资源列表、按时间倒序/按名称排序、查看版本 diff、复制依赖坐标 |
| 管理员 | 项目管理、仓库配置、角色分配、审计日志 |

## 二、设计决策（✅ 已确认）

> 以下 5 项已与需求方确认，作为实现基线。

### 决策 1：三端产物形态 ✅
| 平台 | 产物 | 分发方式 |
|---|---|---|
| Android | **AAR**（纯资源二方库） | 本地 / 私有 Maven（`maven { url }` 即可依赖） |
| iOS | **SPM 资源包**（文本包） | 本地路径 / 私有 Git |
| 鸿蒙 | HAR（后续再做） | 私有 ohpm-repo |

**iOS 与 Android 效果对齐**：都是一句依赖声明，升级版本号即得最新资源。

### 决策 2：iOS 走文本包，规避 macOS ✅
纯资源包不需要 Xcode 编译，产物是 `Package.swift` + 资源目录，**整条构建链路无需 macOS**，CI 可全 Linux。

### 决策 3：密度策略 ✅
- iOS 只要 **@2x / @3x**
- Android 只要 **xhdpi / xxhdpi**
- 矢量图只要**一套**
- 源图以 **PNG** 为主

### 决策 4：命名映射层 ✅
```
逻辑名:  home_icon_search
Android: demo_home_icon_search   (全小写 + 下划线 + 库前缀)
iOS:     demoHomeIconSearch      (camelCase + 前缀)
```

### 决策 5：版本与删除策略 ✅
- 每次发布生成**资源快照**，diff 得出新增/修改/删除（开发看到的「更新了啥」）。
- 删除用 **deprecated 软删除**，不物理删除，保证老版本 App 兼容。

### 技术栈（✅ 已确认后端用 Node）
- 后端：**Node.js**（当前实现 Express，可平滑升级 NestJS）
- 前端：Web 面板（MVP 为免构建静态页，后续可升级 React + Ant Design）
- 存储：PostgreSQL + 对象存储 + Redis 队列（MVP 用 JSON 文件 + 本地磁盘）
- 打包：`sharp` 做图像处理；Android 纯 Node 打包 AAR，iOS 生成 SPM 文本包

## 四、技术栈选型

### 前端（Web 面板）
| 项 | 选型 | 说明 |
|---|---|---|
| 框架 | React 18 + TypeScript + Vite | 或 Vue3，中后台生态都成熟 |
| UI 库 | Ant Design / Arco Design | 表格、表单、上传组件开箱即用 |
| 数据层 | TanStack Query + Zustand | 请求缓存 + 轻量状态 |
| 上传 | Uppy 或自研分片上传（tus / S3 multipart） | 支持批量、断点续传、进度 |
| 列表 | 虚拟滚动（react-virtuoso） | 图片网格量大时必需 |
| 预览 | 图片网格 + diff 视图（新增/修改/删除） | 开发端核心体验 |

### 后端
| 项 | 选型 | 说明 |
|---|---|---|
| 语言/框架 | **NestJS（Node + TS）** 起步；团队是 Java 则 Spring Boot | 全栈 TS 开发快，构建脚本同语言 |
| 数据库 | PostgreSQL | 元数据、快照、审计 |
| 对象存储 | MinIO（自建）/ 阿里云 OSS / 腾讯云 COS | 原图 + 缩略图 |
| 缓存/队列 | Redis + BullMQ（或 RabbitMQ） | 构建任务编排、重试 |
| 鉴权 | JWT + RBAC | 设计师/开发/管理员 |

### 构建 & 发布 Worker（容器化）
| 平台 | 容器内工具链 | 产物 | 发布命令 |
|---|---|---|---|
| Android | JDK + Android SDK + Gradle | AAR | `gradlew publish`（maven-publish → Nexus） |
| iOS | **纯 Node/脚本生成文本包**（无需 macOS） | SPM Package / podspec | `git push` 到私有仓库 |
| 鸿蒙 | DevEco SDK + hvigorw | HAR | `ohpm publish` → ohpm-repo |

### 基础设施
- 部署：Docker Compose（起步）→ K8s（规模化）
- 反向代理：Nginx
- CI/CD：GitLab CI / Jenkins / GitHub Actions
- 通知：企业微信 / 钉钉 / 飞书群机器人 Webhook

## 五、关键流程

### 上传流程
1. 前端分片上传 → 对象存储，同时写"待处理"记录。
2. 后端异步任务：内容 hash 去重 → 缩略图生成 → 命名规范化校验 → 多倍图/矢量派生。
3. 生成/更新"草稿快照"，设计师预览确认。
4. 设计师点"发布" → 进入构建流程。

### 发布流程
1. 冻结快照，生成版本号。
2. 向三个 Worker 派发构建任务（并行）。
3. 各 Worker 生成产物 → 推送到对应私有仓库。
4. 记录发布结果 + 生成 changelog。
5. 通知开发（Webhook / 面板红点）。

### 开发消费
```kotlin
// Android (build.gradle.kts)
implementation("com.example.design:assets:1.2.3")
// 使用：R.drawable.demo_home_icon_search
```
```swift
// iOS (Package.swift)
.package(url: "https://git.company.com/design/assets.git", from: "1.2.3")
// 使用：Bundle.module.image(forResource: "home_iconSearch")
```
```json5
// 鸿蒙 (oh-package.json5)
"dependencies": { "@company/design-assets": "1.2.3" }
// 使用：$r('app.media.home_icon_search')
```

## 六、难点清单（按优先级）

### 🔴 P0 级（决定项目能否落地）

**1. iOS 构建环境（macOS 依赖）**
- 传统做法要 Xcode，CI 必须 macOS，成本高、维护烦。
- 破局：纯资源库走 **SPM 文本包 / CocoaPods resource_bundle**，产物是文本 + 资源目录，用脚本就能生成，**彻底绕开 macOS**。

**2. 多倍图 / 矢量派生**
- iOS 要 @1x/@2x/@3x 或 PDF 矢量；Android 要 mdpi~xxxhdpi；鸿蒙按 base/media。
- 源图可能是 SVG / @3x PNG。
- 策略：
  - 矢量优先（iOS 用 PDF，Android 转 VectorDrawable）→ 只维护一套。
  - 复杂插画矢量转换易失真 → 需要"矢量/位图"分级策略。
  - 位图则由 @3x 自动降采样出各密度。

**3. 命名冲突与前缀**
- Android 库资源**全局唯一**，多库合并时同名会冲突 → 必须强制库前缀（`resourcePrefix`）。
- 三端命名规则不同（大小写、分隔符、保留字）→ 需要统一的映射 + 校验层。
- 不同业务线/设计师上传同名图 → 需要命名空间（项目/模块维度）。

### 🟠 P1 级（影响体验与可靠性）

**4. 版本与增量 diff**
- 需要快照 + manifest 才能算出"改了啥"。
- 全量重发 vs 增量发布：初期可全量（简单），后期优化增量。

**5. 资源删除的向后兼容**
- 老 App 还在引用被删的图 → 编译期/运行期崩溃。
- 必须 deprecated 机制 + 灰度移除。

**6. 三端一致性校验**
- 同一批图，三端产物数量/命名要一致，防止某端漏打。
- 发布前做一次"三端对账"。

**7. 异构构建任务编排**
- 三套完全不同的工具链，需要统一的"任务状态机 + 失败重试 + 日志回传"。
- 构建失败要让设计师/开发看到明确原因。

### 🟡 P2 级（工程化完善）

**8. 私有仓库搭建（三套）**
- Maven（Nexus）、SPM/Specs（Git）、ohpm-repo，各自有配置和维护成本。

**9. 大文件上传与存储成本**
- 分片上传、秒传（hash 去重）、缩略图、存储生命周期策略。

**10. 权限 / 审计 / 通知**
- RBAC、操作日志、发布通知（Webhook）。

**11. 设计工具集成（进阶）**
- 直接从 Figma / 蓝湖 / 摹客拉取资源，省掉手动上传。
- 这是体验的"降维打击"，但可作为二期。

## 七、分阶段落地建议

### Phase 1 — MVP（跑通一条链路）
- 单平台优先（建议 **Android AAR**，工具链最标准）。
- Web 面板：登录 + 批量上传 + 列表（时间倒序/名称排序）+ 手动触发发布。
- 后端：元数据 + 对象存储 + 一个 Android Worker。
- 目标：设计传图 → 点发布 → 客户端能依赖到。

### Phase 2 — 三端打通
- 补 iOS（SPM 文本包）+ 鸿蒙（HAR）两个 Worker。
- 私有仓库全部就绪。
- 版本 diff 视图 + changelog + 发布通知。

### Phase 3 — 体验与规模化
- 多倍图/矢量自动派生、三端一致性校验、deprecated 机制。
- Figma 集成、增量发布、多项目/多业务线隔离、审计报表。
