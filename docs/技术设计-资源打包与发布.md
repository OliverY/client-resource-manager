# 技术设计：资源打包与发布

本文档说明「上传的 PNG 如何变成三端可依赖的库」这一核心机制，以及生产化的演进路径。

---

## 一、三端产物形态（已确认）

| 平台 | 产物 | 分发 | 客户端接入 |
|---|---|---|---|
| Android | **AAR**（纯资源，无代码） | 本地 / 私有 Maven 仓库 | `implementation("com.example.design:design-assets:1.0.1")` |
| iOS | **SPM 资源包**（文本包，无二进制） | 本地路径 / 私有 Git | `.package(path/url:)` |

> 关键点：两者都是「依赖即得资源」，且 **iOS 不需要 macOS / Xcode 构建机**——产物是文本（`Package.swift`）与资源目录，Xcode 在集成时自行编译资产目录。

---

## 二、密度策略

已确认：**iOS 只要 @2x / @3x；Android 只要 xhdpi / xxhdpi；矢量图只要一套。**

| 逻辑倍率 | Android 目录 | iOS 文件名后缀 |
|---|---|---|
| 2x | `res/drawable-xhdpi/` | `@2x.png` |
| 3x | `res/drawable-xxhdpi/` | `@3x.png` |

派生规则（`lib/image.js`）：

1. 若目标倍率有对应源图 → 直接使用；
2. 否则取**最高倍率的源图**，按宽度等比缩放（Lanczos3）派生。
3. 缩放只降不升（避免放大失真），`withoutEnlargement` 语义由「取最高倍率源」保证。

**一致性规则**：上传更高倍率的新图时，旧的、过期的低倍率源会被丢弃，下次打包自动从高倍率重新派生，避免 `@2x` 与 `@3x` 内容不一致。

---

## 三、命名映射

逻辑名统一为 `snake_case` 小写（`lib/naming.js`）：

```
home_icon_search
  ├─ Android : demo_home_icon_search   （前缀 demo_，全局唯一）
  └─ iOS     : demoHomeIconSearch      （camelCase，前缀 crm）
```

- Android 资源名在整个 APK 内**全局唯一**，不同库同名会冲突，因此必须带库前缀。
- iOS 资产目录名也建议带前缀，避免合并到宿主 App 资产目录时重名。
- 校验项：长度、非法字符、以数字开头、过于通用的保留词。

## 四、Android：AAR 生成

### 4.1 AAR 内部结构

AAR 本质是 ZIP，纯资源库最少需要：

```
design-assets-1.0.1.aar
├── AndroidManifest.xml          # 库清单，合并进宿主
├── R.txt                        # 资源符号表
└── res/
    ├── drawable-xhdpi/*.png
    └── drawable-xxhdpi/*.png
```

- `AndroidManifest.xml`：`<manifest package="com.example.design.assets">`
- `R.txt`：每行一个资源符号，形如 `int drawable demo_home_icon_search 0x0`（最终 ID 由宿主 App 构建时分配）。

### 4.2 本地 Maven 仓库布局

```
maven/
└── com/example/design/design-assets/
    ├── maven-metadata.xml
    ├── 1.0.0/design-assets-1.0.0.aar + .pom
    └── 1.0.1/design-assets-1.0.1.aar + .pom
```

宿主工程把该目录配成 `maven { url }` 即可解析依赖。

### 4.3 两条构建路径

| 路径 | 是否需要 Android SDK | 适用 |
|---|---|---|
| 纯 Node 打包（当前实现） | 否 | 纯资源库，无 Kotlin/Java 代码 |
| Gradle 模块构建（预留 `generateGradleModule`） | 是 | 库内含代码、需要 AGP 校验 |

> 纯 Node 路径让 MVP 零依赖跑通；一旦库内要放代码，切 Gradle 即可，产物格式一致。

## 五、iOS：SPM 资源包生成

```
DesignAssets/
├── Package.swift
└── Sources/DesignAssets/
    ├── DesignAssets.swift                     # 自动生成的访问器
    └── Resources/
        └── Assets.xcassets/
            ├── Contents.json
            └── demoHomeIconSearch.imageset/
                ├── Contents.json              # 声明 1x/2x/3x
                ├── demoHomeIconSearch@2x.png
                └── demoHomeIconSearch@3x.png
```

`Package.swift` 用 `.process("Resources")` 把资产目录编进 bundle；使用方通过 `Bundle.module` 访问。

自动生成的 `DesignAssets.swift` 提供对标 Android `R.drawable.xxx` 的访问器：

```swift
public enum DesignAssets {
    private static let bundle = Bundle.module
    public static var demoHomeIconSearch: UIImage? {
        UIImage(named: "demoHomeIconSearch", in: bundle, compatibleWith: nil)
    }
}
```

## 六、版本、快照与 diff

- 每次发布生成一个**资源快照**（逻辑名 + hash + 尺寸 + 各倍率源），存入 `releases`。
- 版本号：`1.0.<发布序号>`，后续可切 semver 或与 Git tag 关联。
- diff：对比两版快照，按 `logical + hash` 得出 **新增 / 修改 / 删除**，即「开发看到的更新了啥」。
- hash 取最高倍率源文件内容的 SHA1。

---

## 七、删除策略

**不做物理删除。** 老版本 App 仍可能引用被删资源，直接删会导致编译失败。

当前实现：`status = removed` 的资产不进入快照（不打包），但元数据保留，可一键恢复。生产环境建议加「废弃 → 下个大版本才真正移除」的窗口期。

## 九、生产化演进路径

1. **存储**：JSON 文件 → PostgreSQL（资产 / 快照 / 审计），原图 → 对象存储（MinIO / OSS），上传走分片 + 秒传。
2. **构建**：打包逻辑抽成独立 Worker，用队列（BullMQ）编排；Android/鸿蒙 Worker 容器化，iOS 走文本包保持无 macOS 依赖。
3. **分发**：Android 推 Nexus/Artifactory；iOS 推私有 Git 或 SPM registry；发布后 Webhook 通知（企微 / 钉钉 / 飞书）。
4. **权限**：接入 SSO，后端强制 RBAC（当前角色仅前端切换），补审计日志。
5. **体验**：版本 diff 高亮缩略图对比、资源标签/搜索、批量替换、设计工具（Figma）直连。
